= libre-bm6 Implementation Log
A factual record of how the code under `packages/` was written from the two specification files, what the implementers read, and what was verified.

== Scope and conventions

This log covers the implementation side only. The specification side keeps its own log, which the implementers did not read.

* Dates are 2026-11-14 unless stated otherwise. Times are local.
* The device address is written `A1:B2:C3:D4:E5:F6` throughout. The real address is not recorded in this repository.
* "Observed" means seen on real hardware with this repository's own code.

== Clean-room controls

=== Who did the work

The work was done in one AI coding-agent session directed by Tag. The session planned, briefed, and verified. It delegated the writing, reviewing, and fixing to subagents, each started with no prior context and a brief that repeated the clean-room rule.

The session listed the names of tracked files outside `cleanroom/` once, without opening them.

=== Network lookups

* One web search on the licensing of BLE plugins, with results from pub.dev and GitHub.
* The pub.dev API pages for `universal_ble` and `pointycastle`.

=== How this was checked

Every subagent reported the files it opened and the URLs it fetched. Each report matched the lists above. These are the agents' own accounts. Their transcripts were not audited.

=== Caveat

An AI model cannot attest to what was in its training data. Public material about this device may exist. The briefs told every agent to implement only what the two specification files say.

== Decisions

Tag made these before any code was written.

* Two packages: a pure Dart codec, and a Flutter adapter on `universal_ble`.
* `universal_ble` (BSD-3-Clause) over `flutter_blue_plus`, because `flutter_blue_plus` 2.x left BSD for its own license with a paid commercial tier.
* Active mode sends only `D1 55 07`. There is no retry, fallback chain, watchdog, or reconnect. Callers handle those.
* The library stays primitive, with the least code needed to read from the device.

The session made these.

* AES through `pointycastle`, not a hand-written cipher.
* Every field the specification documents for the two frames is exposed.
* The decrypted MAC is exposed and never compared to the platform device ID, because iOS reports no MAC.
* Status stays a plain integer.

== Hardware testing

Tested on one BM6 unit in a car, from a Linux laptop (Debian, BlueZ, `universal_ble` 3.3.0 Linux backend), with no bonding. Three runs of the smoke tool and one capture run. Run the tool from `packages/libre_bm6_universal_ble` with `flutter test tool/smoke.dart`.

The tool runs under `flutter test` because `universal_ble` imports Flutter and cannot run under plain `dart run`. It overrides the target platform to Linux so that the real BlueZ backend is selected.

Observed:

* The device advertised as `BM6`. The decrypted MAC equaled the device ID in every event.
* State of charge was 100 % and status was 2 throughout. Cranking voltage and cranking status were 0.
* The single `D1 55 07` write was enough. The acknowledgement arrived ~1.1 s after connect, and the first data frame ~0.9 s after that.
* Write without response on `FFF3` worked, although the stack reports only `write` on it.
* Byte 13 of every data frame was `0x02`, and bytes 14 and 15 were `0x00`.
* The GATT table matched the specification. The firmware-update service was not touched.
* The disconnect event arrived twice, ~1 ms apart.
* Notifications kept arriving during the ~2 s that cancel took.
* An example data frame: `D1 55 07 00 0C 02 64 05 80 00 00 00 00 02 00 00`, which is 12 °C, status 2, 100 %, 14.08 V.

Not tested: negative temperatures, status 1, a stream longer than ~30 s, and iOS.

=== Android

* On 2026-11-14 the adapter was exercised on a Pixel phone running Android 17 through `universal_ble` 3.3.0.
* Passive scan found and decoded the monitor with `BLUETOOTH_SCAN` flagged `neverForLocation` and no location permission.
* The phone connected in ~1.7 s, discovered services, and subscribed to `FFF4`.
* The write without response was then rejected by the plugin's Android backend, because `FFF3` declares only `write`.
* The adapter now writes with response. The smoke tool was re-run on Linux with the write with response in two runs, with 26 and 19 live frames, a mean interval of ~1000 ms, and 0 errors.
* The monitor's address type is public.
* Connection attempts made out of range ended with Android status 147 (connection timeout) after 30 s each.

Confirmed later the same day: with the write-with-response, the phone connected in ~1.6 s, discovered services, subscribed to `FFF4`, and held the connection. Live readings arrived and were displayed.

=== The capture

The capture holds the raw scan results, the notifications as ciphertext and plaintext, the connection events, and the GATT table. It was sanitized before it was committed.

* Each encrypted advertisement block was decrypted, its MAC bytes replaced with `A1 B2 C3 D4 E5 F6`, and re-encrypted.
* The iBeacon payload was replaced with zero bytes.
* The file, the smoke tool, and the tests were searched for the real address in every form, with no hits.

Working logs that contain the real address were kept outside the repository.

== Known limits

* Passive mode on Linux is suited to testing only. BlueZ keeps every block it has seen, never dropped one during the test (the list grew from 12 to 15 entries), and gives no signal for which is current. Android is the next test target.
* On Linux, `liveData()` needs a scan first in the same process.
* A device with no OS-reported name is skipped, because `universal_ble` does not expose the raw advertisement record. `decodeScanRecord` covers stacks that do.
* There is no checksum in the protocol. A block from another device that passes the service and name filters decodes as garbage. The caller's MAC comparison is the only guard.

== Feedback for the specification side

These are hardware observations for Tag to relay.

* The BlueZ platform note says to track which entries are new, or pick the latest. That is not sufficient. A recurring reading reuses its earlier key, and BlueZ does not reorder or drop entries.
* Whether the device keeps advertising while connected is still unsettled. No new block appeared during either connected session.
* `FFF3` accepts a write with response, observed on Linux. Through `universal_ble` on Android a write without response is refused client-side because the characteristic declares only `write`.
* Advertisement and live voltages agreed in range. They were not compared at the same instant.
